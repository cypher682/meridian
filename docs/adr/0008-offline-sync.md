# ADR-0008: Offline front-desk writes and replay

- Status: Accepted
- Date: 2026-10-20
- Supersedes: the offline-sync deferral in ADR-0001 for front-desk writes

## Context

ADR-0001 deferred offline sync until the local clinical flow worked. The local
flow now covers registration, encounters, lab results, amendments, HL7, FHIR,
billing, and pharmacy. The remaining product risk is what happens when the API
or network disappears while the front desk is working.

The current constraints are:

- The SPA is served by the API and uses Keycloak access tokens in memory.
- Every write is facility-scoped and appends an audit entry in the same database
  transaction.
- Resource ids are generated by PostgreSQL or the service, so an offline client
  cannot know the id of a patient it just registered.
- Retrying a write after a timeout can create a duplicate patient, encounter,
  invoice, or audit entry.
- Front-desk writes have dependencies: an encounter needs a patient, an invoice
  needs an encounter, and a charge needs an invoice.

Offline support cannot be a second write path with different rules. Replayed
writes must produce the same rows and audit entries as online writes.

## Decision

### Scope

The first offline slice is limited to an already-open, authenticated front-desk
session:

- Register a patient.
- Create an encounter.
- Create an invoice, add charges, and mark it paid.

These workflows stay online-only:

- Lab ordering, collection, resulting, release, and amendments.
- HL7 ingestion and FHIR reads.
- Pharmacy item, stock, and dispense writes.
- Audit verification.
- Any write by a role other than front desk or admin.

Offline cold start is not part of this slice. The SPA must have loaded and
authenticated before connectivity is lost. Persisting access or refresh tokens
in browser storage is rejected; a reload while offline may show the cached shell
only after a later phase, and the user must reconnect to sign in.

### Client-generated ids

Create requests accept an optional UUID `id`:

```text
POST /api/patients                  { id?, givenName, familyName, dateOfBirth, phone }
POST /api/encounters                { id?, patientId, clinicianId, notes, vitals }
POST /api/billing/invoices          { id?, encounterId }
POST /api/billing/invoices/{id}/charges { id?, description, amountCents }
```

The browser generates the UUID before the first attempt and reuses it for every
retry. The server uses the supplied id when present and falls back to its current
id generation when absent. This removes temp-id remapping and lets an offline
encounter reference an offline patient immediately.

The server treats the id as an idempotency key:

- If the id does not exist in the caller's facility, insert it and audit normally.
- If the id exists with the same normalized payload, return the existing row and
  do not write a second audit entry.
- If the id exists with a different payload, or exists in another facility,
  return `409` without exposing the other facility's data.
- If a unique business constraint fails, such as a second invoice for the same
  encounter, return `409`.

No generic idempotency table is added. The entity primary key is the replay key
for creates. Payment is made idempotent separately: paying an already-paid invoice
returns the invoice when the recorded payer is the current actor, and returns
`409` when another actor paid it.

### Local outbox

The SPA writes queued operations to an IndexedDB `outbox` store before attempting
the network call. An entry contains:

```text
operationId, facilityId, actor, type, path, body, targetId, parentId, capturedAt,
status, attempts, nextAttemptAt, lastError
```

`status` is `pending`, `syncing`, or `failed`. `type` covers patient
registration, encounter creation, invoice creation, charge creation, and
payment. The queue is FIFO within a facility and actor so a patient is created
before its encounter, and an encounter before its invoice.

Replay rules:

- A single flusher is elected with the Web Locks API; other tabs wait.
- The flusher requires a valid Keycloak token and matching `facility_id` and
  `preferred_username` claims. A mismatch pauses the queue instead of replaying
  another user's writes.
- Network errors, `408`, `429`, and `5xx` are retryable with exponential backoff.
- `400`, `403`, `404`, and `409` are non-retryable. The entry becomes `failed`,
  is shown to the user, and blocks later entries for that facility and actor so
  dependencies are not reordered.
- `401` pauses the queue and asks the user to sign in again.
- Successful creates are merged back into the local cache and UI. A failed entry
  is never silently dropped.

### Read cache

The SPA caches only the data needed by the offline front desk: patients,
encounters, invoices, and charges, keyed by facility. Successful GET responses
refresh the cache. While offline, patient search, chart encounters, and invoice
lists read from the cache. Cached rows that have not synced are marked as
pending.

Cache data is scoped by facility and cleared when the user signs out. The demo
database contains synthetic data only. IndexedDB is not encrypted and is
accessible to same-origin script, so this design must not be used with real
protected health information until storage encryption and a formal threat model
exist.

### Audit and time

The server remains authoritative for row timestamps and audit time. Each
replayed write adds `source: "offline"` and the client's `capturedAt` to the
audit payload, but the audit chain uses server time and the token actor. The
audit entry is appended only when the row is inserted, so a duplicate replay
does not create a second entry.

The queue stores the actor and facility at capture time. A different user cannot
flush it. If the original user cannot sign in again, the queue remains local and
visible until they do, or until it is explicitly discarded with confirmation.

### Service worker

The first slice does not add a service worker. Offline work is supported while
the tab and session are alive. A later phase may cache the app shell for reloads,
but it must not cache authenticated API responses in the service worker and must
not persist Keycloak tokens.

## Consequences

- Front-desk registration, encounters, and billing survive short outages without
  duplicate rows or audit entries.
- The browser owns ids for offline-created rows. UUIDs are opaque; the server
  still enforces facility scope and payload consistency.
- A permanent rejection blocks the queue until the user resolves it. This is
  deliberate: silently skipping an encounter can orphan its invoice.
- Cached clinical data remains on the device until sign-out. This is acceptable
  only for the synthetic demo, not for production PHI.
- Offline actions are audited at replay time, with the original capture time
  recorded in the payload. The two times can differ.
- Multi-device editing, merge conflicts, background sync, and offline lab or
  pharmacy writes remain out of scope.

## Alternatives considered

- Server-generated ids plus a local temp-id map: rejected because every dependent
  payload would need rewriting at replay and failures would leave partial maps.
- A generic idempotency table storing response bodies: workable, but more
  infrastructure than the four create operations need. Entity ids provide the
  same guarantee with no new table.
- Persisting Keycloak refresh tokens for offline cold start: rejected because a
  public SPA cannot protect long-lived tokens in browser storage.
- Background Sync API: rejected as the primary mechanism because support and
  timing are browser-dependent; the in-tab outbox is deterministic and testable.
- CRDT or field-level conflict resolution: rejected because this slice only
  creates append-only records and a simple status transition, not concurrent
  edits.
